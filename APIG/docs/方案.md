# 影腾摄像头客服 Agent Demo 方案

## 1. 项目目标

影腾是监控摄像头解决方案提供商，希望在已有 Web 系统中叠加客服 Agent，为最终用户提供产品答疑和故障诊断。本项目当前交付一个具备监控行业属性的模拟 Web 存量系统，通过 AgentKit HTTP 转 MCP 将 REST API 转换为 Agent 工具，通过模型网关提供统一模型接入和主备 Fallback，最终完成一条可验证、可讲解的端到端 Demo。原生 App 不属于本次作业范围。

一期只实现 Web 控制台和模拟数据，不连接真实摄像头、不处理 RTSP 视频流，也不声称具备真实视觉诊断能力。

## 2. 一期范围

一期提供运营总览、摄像头列表、设备详情、告警中心、API 调用审计和 AI 诊断抽屉。业务后端提供查询设备、获取诊断指标、查询告警和更新检修状态等 REST API。云端入口使用 AgentKit Runtime API Key 鉴权。

Agent 可以完成设备定位、状态查询、故障诊断和处置建议。将摄像头标记为待检修属于写操作，必须在用户确认后执行。模型网关配置主模型和备用模型，并通过故障注入验证 Fallback。

## 3. 架构

```text
最终用户
  │
  ▼
摄像头管理 Web / Agent 对话入口
  │                         │
  ▼                         ▼
模拟存量 REST API      AgentKit Runtime Agent
  ▲                         │
  │ Runtime API Key         ▼
HTTP 转 MCP 服务 ◀──── MCP 工具集
                            │
                            ▼
                  模型网关主模型 → Fallback 备用模型
```

存量系统通过 Runtime 网关对公网入口执行 API Key 鉴权；MCP 网关负责把 OpenAPI 定义转换成工具，并在出站请求中注入托管的 Runtime API Key；Agent 通过 MCP 工具集访问业务系统；模型网关承接模型代理、Proxy Key 和 Fallback。

## 4. 模拟业务数据

Demo 预置 6 台摄像头，覆盖上海一号园区和杭州研发中心。重点故障设备是园区西门 `CAM-003`：供电和本地存储正常，但网络丢包率为 38.4%、延迟为 486 ms，导致画面间歇中断。停车场北区 `CAM-004` 离线 38 分钟，已处于待检修状态。

诊断接口返回供电、网络、丢包、延迟、存储、温度和画面状态。数据全部为确定性的模拟数据，确保现场演示稳定。

## 5. API 与 MCP 工具

| HTTP API | MCP operationId | 用途 | 写操作 |
|---|---|---|---|
| `GET /api/cameras` | `list_cameras` | 按状态或关键词定位设备 | 否 |
| `GET /api/cameras/{camera_id}` | `get_camera` | 查询设备详情 | 否 |
| `GET /api/cameras/{camera_id}/diagnostics` | `diagnose_camera` | 获取诊断指标与建议 | 否 |
| `GET /api/alerts` | `list_camera_alerts` | 查询全部或指定设备告警 | 否 |
| `PATCH /api/cameras/{camera_id}/maintenance-status` | `update_camera_maintenance_status` | 更新检修状态 | 是 |

`openapi.yaml` 可直接用于 AgentKit 的 HTTP 转 MCP。生产或云端联调时，应将 `servers.url` 修改为 AgentKit 网关可访问的 HTTPS 地址。

## 6. 安全设计

AgentKit Runtime 在请求到达应用代码前校验 API Key。MCP 服务侧托管真实 Runtime API Key，并通过出站凭据注入 `Authorization: Bearer <Runtime API Key>`，Agent 和最终用户不接触密钥。应用不再重复维护第二套静态 Key。

API 审计记录请求时间、Method、Path、Query、Body、状态码、耗时和认证结果，但不记录 API Key 或 Authorization 原文。Demo 使用静态密钥，暂不实现 HMAC、AK/SK 或动态签名，避免 HTTP 转换造成 canonical request 不一致。

## 7. Agent 行为约束

Agent 回答设备问题前必须调用工具获取事实，不能凭空生成设备状态。诊断按“定位设备—查询详情—获取诊断—查询告警”的顺序收集证据。Agent 必须区分供电、网络、存储和画面问题，并明确一期没有分析真实视频。

更新检修状态之前必须获得用户明确确认。没有确认时只提供建议，不调用写工具。

## 8. 模型网关与 Fallback

模型网关创建主、备两个模型配置，对 Agent 暴露统一 Base URL、模型路由名和 Proxy API Key。主模型应配置更高优先级，备用模型只在主模型出现可重试故障时接管。

Fallback 验收采用可恢复的故障注入：临时将主模型 API Key 改为无效值，或暂时指向返回 5xx 的测试接入点；然后向 Agent 发起“园区西门为什么没有画面？”的请求。验收标准是业务回答仍成功、模型网关日志显示主模型失败和备用模型接管、Agent MCP 工具调用仍完整。测试结束后立即恢复主模型配置。

不建议用错误的模型 ID 模拟所有场景，因为部分 4xx 可能被判定为不可重试错误，不会触发 Fallback。具体可重试状态码以当前模型网关策略为准。

## 9. 控制台配置步骤

### 9.1 HTTP 转 MCP

1. 将 Demo 后端部署到 AgentKit 可访问的地址，并确认 `/health` 返回正常。
2. 修改 `openapi.yaml` 的 `servers.url`。
3. 在 AgentKit 的“网关—MCP 服务”中创建 HTTP 转 MCP 服务。
4. 上传 `openapi.yaml` 并确认生成 5 个工具。
5. 创建出站 API Key 凭据，Header 名设置为 `Authorization`，值设置为 `Bearer <Runtime API Key>`。
6. 逐一调试查询工具，再测试更新检修状态。
7. 创建 MCP 工具集并加入上述工具，按需配置入站认证。

### 9.2 模型网关

1. 创建模型网关并添加主模型、备用模型。
2. 为 Demo Agent 创建最小权限 Proxy API Key。
3. 配置健康检查、重试和 Fallback 顺序。
4. 获取 OpenAI-compatible Base URL 和模型路由名。
5. 将 Base URL、Proxy Key、模型路由名配置到 AgentKit Runtime。

### 9.3 AgentKit Runtime

1. 使用 `agent/camera_agent.py` 创建 Agent 工程。
2. 在 Runtime 中关联 MCP 工具集。
3. 将模型配置指向模型网关，不直接使用供应商真实 API Key。
4. 发布后使用固定 `user_id` 和 `session_id` 测试多轮对话。

## 10. 演示脚本

演示者先打开运营总览，说明系统是模拟的存量摄像头管理平台，现有业务 API 使用 API Key 保护。随后打开 AI 诊断助手并提问：“园区西门为什么没有画面？”

Agent 应先定位 `CAM-003`，再查询设备详情、诊断指标和近期告警，最后回答：供电和存储正常，网络丢包率 38.4%、延迟 486 ms，画面中断主要由网络异常导致，并给出检查交换机端口、网线和恢复后重新拉流的建议。

演示者再说：“把它标记为待检修。”Agent 应请求确认；确认后调用写工具。刷新控制台，设备检修状态变为“待检修”。进入 API 审计页面，可展示 MCP 对存量系统实际发出的 Method、Path、状态码和耗时。

最后执行模型 Fallback 演示：制造主模型可重试故障，重复诊断问题，证明备用模型接管后业务链路仍然完成，并在模型网关日志中展示切换证据。

## 11. 验收标准

- Web 控制台可以展示摄像头、状态、诊断和告警。
- 未携带或携带错误 Runtime API Key 时，由 Runtime 网关拒绝请求。
- OpenAPI 文件可生成预期 MCP 工具。
- Agent 能基于 MCP 返回的真实模拟数据回答，不编造指标。
- 写操作必须经确认，状态更新后控制台可见。
- 审计页面可显示 HTTP 调用链且不泄露密钥。
- 模型网关主模型故障时，备用模型成功接管并保留日志证据。

## 12. 后续演进

后续可以接入真实摄像头设备平台、RTSP/GB28181 状态、视频截图和视觉模型，形成画面遮挡、模糊、偏色和异常事件诊断。进一步可拆分设备 Agent、网络诊断 Agent 和工单 Agent，通过 A2A 网关进行注册、发现与协作。
