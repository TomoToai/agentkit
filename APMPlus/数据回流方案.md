# 影腾摄像头诊断 Agent · 数据回流方案

> 依据火山引擎官方文档《数据回流》（<https://docs.volcengine.com/docs/86681/2663805>）落地。
> 目标：把摄像头诊断 Agent 线上真实 Trace 批量导出成评测集「影腾摄像头诊断-真实回流集」，
> 与方式一（人工设计集 `eval/`）互补，复用同一套评估器形成「线上真实数据 → 评测验证」闭环。

## 一、什么是数据回流（官方定义）

在分布式可观测场景中，线上 Trace 反映了性能瓶颈、异常调用与服务依赖关系。
**数据回流** = 将线上 Trace 数据**批量导出到评测集**，形成标准化、可复用的链路样本库，
再基于这些真实样本发起评测实验，用于：链路诊断验证、检测规则优化、异常识别效果评估、
故障案例沉淀与复现。

## 二、两条硬限制（务必先记住）

| 限制 | 说明 | 对我们的影响 |
|---|---|---|
| **仅回流新数据** | 导出规则只作用于**任务创建之后**产生的 Trace，不支持历史数据 | **必须先建导出任务，再跑 `replay_traffic.py` 造流量**，否则本次流量全漏 |
| **总量/单次上限 100000 条** | 总上限与单次导出上限均为 10 万条，可自定义，超出部分导出失败 | 我们仅 28 条回放，远低于上限，无需分批 |

## 三、操作步骤（控制台）

1. 登录 [AgentKit 控制台](https://console.volcengine.com/agentkit)。
2. 左侧导航栏选择 **可观测 → 数据回流**。
3. 单击 **创建导出任务**，按下表配置参数，完成后单击 **确定**。
4. **任务创建成功后**，再执行本目录的造流量脚本（见第六节），让符合筛选条件的新 Trace 被捕获导出。

## 四、创建导出任务参数（官方字段 → 本项目取值）

| 分类 | 配置项 | 官方说明 | 本项目取值 |
|---|---|---|---|
| 基础信息 | 任务名称 | 自定义 | `camera-agent-reflow` |
| 基础信息 | 数据总上限 | 每任务最多 100000 条，可调 | 保持默认（远超本次 28 条） |
| 数据过滤 | 数据过滤 | 支持 8 个筛选项：**Span 类型 / AI Span 类型 / 服务名称 / 模型名称 / 接口名 / 状态码 / 操作 / 耗时**；同项多条按“或”，跨项按“与” | **服务名称** 包含 `yingteng-camera-ai-diagnosis`（真实服务名带前缀 `r-yesysnbwg...`，用「包含」即可命中；亦可改用左侧「Runtime 名称」精确锁定）；**AI Span 类型** = `agent`（❗真实枚举为 `agent`/`workflow`/`agent_server`/`llm`/`tool`，**没有 “Agent Run”**；`agent` 类型的一条 span = 一轮完整问答，正是评测样本粒度）；**状态码不要过滤**（真实状态码取值为 `0`/`1` 而非 200，且顶层 `agent`/`workflow` span 反而是 `1`，按状态码过滤易误排要保留的样本） |
| 时间范围 | 回流新数据 | 规则应用于后续产生的符合条件 Trace | 选用（唯一支持项） |
| 时间范围 | 总时间范围 | 指定导出数据的总时间范围 | 覆盖本次造流量的时间窗（建议留足 1~2 小时） |
| 时间范围 | 重复频率 | 不重复 / 按天 / 按周 | **不重复**（一次性造流量，无需周期导出） |
| 导出配置 | 导出平台 | 导出到智能体评测平台 | 智能体评测平台 |
| 导出配置 | 数据脱敏 | 开启（默认）自动脱敏 Input/Output；关闭可导出完整内容便于调试 | **开启**（生产默认，保护敏感数据） |
| 导出配置 | 目标评测集 | 选已有或新增（新增需自定义名称） | **新增** →「影腾摄像头诊断-真实回流集」 |
| 导出配置 | 导入方式 | 目前支持追加，在已有数据基础上追加 | 追加 |
| 导出配置 | 字段映射 | 依次选择 Trace Span 字段 → 评测集字段 | Span `input` → 评测集 `input`；Span `output` → 评测集 `reference_output`（见第五节） |

> **为什么 AI Span 类型只选 `agent`，不多勾几种？**
> 一次用户提问在内部被拆成多层 span，它们的 input/output 完全不是同一种东西：
> - `agent`（也含 `root`）：input = 用户原话、output = 最终回答 → ✅ 正是 Q→A 评测样本；
> - `llm` / `llm_loop`：input 是拼好的大段 prompt、output 是模型中间文本 → ❌ 不是用户问题；
> - `tool`：input/output 是工具调用/返回 JSON（`{"name":"list_cameras"...}`）→ ❌ 不是问答。
>
> 多勾类型**不会让数据集更丰富，只会更脏**：同一个问题会按 span 层数被拆成 5~9 行，
> 去重后还是原来那些问题，数量虚涨、人工审核量翻倍，还混入无法评测的工具 JSON。
>
> **真正的“丰富”来自造流量侧加题**——往 `eval/camera_agent_eval_set.csv` 加更多、更
> 多样的问题（不同设备/故障/边界/越权试探）再回放，或让真实用户多用一段时间自然沉淀。
> 过滤侧只留 `agent` 即可，工具调用轨迹已包含在 agent span 内，工具合规评估无需单独抓 tool span。
> 若确需**步骤级**样本（专门评工具调用），应另建评测集、配不同评估器，不要与问答样本混在一起。
>
> 兜底：即便控制台误勾了 llm/tool，本地 `process_reflow.py`（默认 `--span-type agent`）会在
> 导出后剔除非 agent span 及 input 为工具 JSON 的脏行。

## 五、字段映射与评测集列对齐

回流评测集列结构与方式一（`eval/camera_agent_eval_set.csv`）保持一致，便于复用评估器：

| 评测集列 | 来源 | 说明 |
|---|---|---|
| `input` | Trace Span 的用户输入字段 | 用户问题原文 |
| `reference_output` | Trace Span 的 Agent 输出字段 | **回流的是 Agent 真实回答，需人工审核/修正为标准答案后**才可作为参考答案 |
| `case_id` | 加工时生成 | `REFLOW-001…`（本地 `process_reflow.py` 产出）或平台自动编号 |
| `category` / `difficulty` | 人工补充 | 与方式一对齐的自定义维度，导入后手动补 |

> 若在控制台完成脱敏与字段映射后直接得到评测集，可跳过本地 `process_reflow.py`；
> 本地脚本用于**二次清洗/自测**（去重、剔探测性输入、补一层 PII 兜底）。

## 六、造流量（本目录脚本）

先确认导出任务已创建，再执行：

```bash
set -a && source ../.env && set +a    # 载入 REPLAY_USER / REPLAY_PASS
python3 replay_traffic.py             # 逐条回放 eval/ 题库 → 触发全链路真实 Trace
```

- 每条问题独立 `session_id`（`eval-replay-<case_id>`），保证每轮是完整独立 Agent Run，回流不串题。
- `user_id` 统一为 `eval-replay`，便于回流按维度圈出这批流量（如需可在数据过滤加自定义维度）。
- 顺序执行 + 间隔（默认 2s），护单实例 Runtime；支持断点续跑与失败重试。

### 造流量避坑清单（实测踩过的坑）

1. **先建任务、再造流量**：回流「只应用于后续新产生的 Trace」，任务创建前打的流量一律捕获不到。
2. **触发周期必须选「不重复」**：若误选「按天重复」，任务会变成按天调度的批处理，当天造的流量要
   等次日 00:00 才处理，表现为「进行中但总数 0」。改回「不重复」后需**重新造流量**——已产生的
   历史 Trace 未必回溯。
3. **改了触发方式/过滤后要重造流量**：规则变更只对其后新到达的 Trace 生效。
4. **断点续跑会跳过已成功题**：`replay_result.jsonl` 里 HTTP 200 的 case 会被视为已完成而跳过。
   要重新造一批全新流量时，先归档旧结果：
   `mv replay_result.jsonl replay_result.$(date +%H%M%S).bak`
5. **过滤 value 用「包含」**：真实服务名带前缀 `r-yesysnbwg....yingteng-camera-ai-diagnosis`，
   用「等于」会匹配不到。
6. **入库有延迟**：造完流量到列表总数增长有几十秒~几分钟延迟，别秒刷；可先去「可观测 → Trace
   查询」按 user_id=`eval-replay` 确认 Trace 已入库，再等回流导出。

## 七、加工与导入（可选的本地二次清洗）

```bash
# 导出文件 → 干净 CSV（去重 / 剔无效 / PII 脱敏）
python3 process_reflow.py -i <导出的Trace文件.jsonl>
# 或用回放自测数据
python3 process_reflow.py --only-success --source-tag replay
```

产物 `real_reflow_eval_set.csv`（UTF-8 BOM）：**人工审核 `reference_output` → 补维度列 →
导入/追加到评测集 → 提交版本 → 复用三个评估器（事实正确性 / 工具合规 / 安全边界）跑实验**。

## 八、与方式一的关系

| 维度 | 方式一（`eval/`） | 方式二（本目录，数据回流） |
|---|---|---|
| 数据来源 | 人工设计（28 条覆盖正常/边界/安全） | 线上真实 Trace 回流 |
| 标准答案 | 人工预先写定 | Agent 真实回答，需人工审核修正 |
| 评估器 | 事实正确性 / 工具合规 / 安全边界 | **同一套复用** |
| 定位 | 覆盖度、回归基线 | 真实分布、故障复现、持续补集 |
